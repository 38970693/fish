## 主菜单溢出修复（续 09-15）：从「能滚」到「根本不用滚」

用户接着提了新要求：**「不要滚动，左右可以做宽一点」** —— 09-15 那两刀（可滚动容器 + 压缩字号）
只做到「滚得到」和「1440×900 放得下」，1280×560 仍溢出 37px，而且靠压字号治标不治本。

### 这一轮改的是结构，不是字号
| 改动 | 效果 |
|---|---|
| 鱼塘卡 `w-56` → `w-72`，容器 `max-w-3xl` → `max-w-[912px]` | 卡内文字少换行，区块高 **145 → 108** |
| 初始鱼容器 `max-w-3xl(768)` → `max-w-6xl(1152)` | 11 条鱼从两行变**一行**（~220 → 107） |
| 开始游戏 / 装扮 / 规则·成就·排行榜 合成**一行底栏** | 省两行 |
| 纵向节奏再收（标题 lg 以下降档、gap、内距、底栏上边距） | 再省 ~30 |

**内容高 940 → 494。** 实测 1440×900 / 1280×720 / 1280×560 / 1024×700 **全部 overflow=0**。
外层 `overflow-y-auto` 保留但**降级为兜底**（只有视口真矮到装不下才滚），注释里写清别再退回竖向长条。
提交：`d199eff`。

### 关键教训
1. **居中布局的「截断」有三层需求，只做前两层都不算完**：① 滚得到（可达性）→ ② 装得下（观感）
   → ③ **结构性地矮下来**（用户真正在意的）。压字号只能到②，要③必须**改布局方向：竖向堆叠 → 横向铺开**。
2. **「卡片太窄导致文字换行」是隐藏的高度杀手**：鱼塘卡从 w-56 加宽到 w-72，高度反而降了 37px。
   想压矮一个区块，先试试让它变宽。
3. **别用 `getBoundingClientRect().top` 去重数行数**：选中态带 `scale-110` 会让 top 差几像素，
   11 个一行会被误判成 2 行。要数行就用容器 `offsetHeight`。

### 回归锚拆成两条（e2e/game-flow.spec.ts，20 → 21 例）
- ① **常见视口不滚动**：1280×560 / 1440×900 要求「标题顶 → 开始按钮底」全在视口内。
- ② **极端矮视口仍可滚**：1280×420 下先断言溢出成立，再要求头尾都能滚进视口。
  少一条就退化：只有①漏掉「内容变高但还能滚」；只有②重演「没有可滚祖先」的死局。
  （原用例只测②且写死 560，菜单变矮后它会因为「不溢出」而空转 —— 已删。）

## G1 放行条件台架：收尾（worker RPC 超时根治 + 文档纠偏）

### 根治「18 例全绿但退出码非 0」
报错 `Error: [vitest-worker]: Timeout calling "onTaskUpdate"`。**不是 testTimeout 太短**（提到 30 分钟
也没用），真因在 birpc 的 **60 秒 RPC 应答计时**：

1. worker 调 `rpc().onTaskUpdate(...)`，birpc 起 60s `setTimeout` 等主线程应答；
2. 主线程**早就应答了**，但 worker 在跑同步循环，IPC 消息收不进来；
3. 循环结束事件循环恢复 —— **timers 阶段排在 poll（I/O）之前**，那个早已过期的定时器
   **先于**躺在队列里的应答触发 → 判超时。

所以**「把用例拆细」治标不治本**：拆到每组 95~123 秒仍 > 60 秒，实测照样报。
根治：台架在**每个种子之间**让出一次事件循环（`breathe()` = `await new Promise(r => setTimeout(r, 0))`，
约 15 秒喘一次）。⚠️ **只能在种子之间让，不能在帧循环里让** —— `withSeededRandom` 期间 `Math.random`
被 mock，中途让出会污染别的代码。
结果：**18 passed，Errors 0**，且数字与上一轮逐字节一致（说明 breathe 只改管道不改结果）。
另：把 `runsOf` 拆成 `await ensureArm(k)`（异步跑 + 缓存）与同步 `runsOf(k)`（取数，没跑就抛错），
改动面最小。

## 「布局有点丑」→ 老板要的是**对称**
发了截图但我**读不了图**（本次会话模型不支持读图）。先给了三个参考方向
（A 英雄展示位/原神式，B 极简两步/任天堂·Duolingo，C 卡片网格/Steam 式），
老板回了三个字：**「都没有对称」**。

### 不对称的真正来源（两个都靠测量才发现，肉眼看不出来）
1. **flex 自然宽度**：卡片宽度由文字长短决定，宽窄不一 → 谈不上对称。
2. **更隐蔽的：flex 列默认 `align-items: stretch`**。鱼塘容器 `w-full max-w-[912px]`
   被限到 912（父宽 1052），stretch 下**直接左对齐**，实测中心偏左 **74px**。
   给子项设 `w-full` + `max-w-*` 时，stretch 不会帮你居中 —— 要么 `mx-auto`，要么让 max-w 大于父宽。

### 改法（三块各自选最合适的工具，不是一律 grid）
- 鱼塘：`flex` → **`grid-cols-3`** 三等分 + 卡片去掉自定宽；容器 `max-w-[912px]` → `max-w-6xl`（撑满父宽 1052，顺带和鱼区同宽）。
- 初始鱼：**保持 flex + 卡片定宽 `w-20 flex-none`** —— grid 做不到「最后一行居中」，
  flex-wrap + `justify-center` + 定宽才能在任何断点下让末行居中。
- 底栏：`grid-cols-3` + `order`，装扮贴左列内侧（`justify-self-end`）、开始游戏正居中、
  规则·成就·排行榜贴右列内侧（`justify-self-start`）。
  **用标准 `grid-cols-3`（左右列天然等宽）保证 CTA 落在几何中心，别用 `grid-cols-[1fr_auto_1fr]` 任意值**。

### 对称是量出来的，不是看出来的
写了临时脚本量四组数：每组元素的 `offsetWidth` 去重（1 个 = 等宽）、
`min(left)+max(right)` 的中点 vs `window.innerWidth/2`（0 = 正中）、`offsetTop` 去重判行数。
结果：标题 0 / CTA 0 / 鱼塘 3 张全 343 一行 / 鱼 11 张全 80 一行 / 两块容器同宽 1052。
残余 −4 / −2 来自选中态 `scale-105`、`scale-110` 的外扩（放大必然外扩，是刻意的强调，非布局问题）。
提交：`59d79fc`。

### ⚠️ 判行数别用 `getBoundingClientRect().top`
选中态带 `scale-110`，会让 top 差几像素，**11 个一行会被误判成 2 行**（踩了两次）。
用 **`offsetTop`**（布局位置，不受 transform 影响）。
同理，`getBoundingClientRect().width` 含 transform，测等宽要用 `offsetWidth`。

**另注**：本项目 Tailwind 是 `index.html` 里的 **CDN 版**（`cdn.tailwindcss.com`），
任意值类（如 `w-[88px]`）能生效但实测是 content-box 行为（88 + padding + border ≈ 97），
不确定就改用标准尺寸类（`w-20`）。
