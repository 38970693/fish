## 项目审计：为「下一步做什么」做优先级评估

用户问「下一步哪些最值得做」。没有照抄路线图的 P2 清单，而是重新扫了一遍代码找
「数据配好了但没接线」的东西，结果比路线图上写的更有价值。

### 扫出来的死字段（声明了但全局零读取）

| 字段 | 位置 | 状态 |
|---|---|---|
| `isOverdrive` | PlayerState | 只在 `initialState.ts` 赋值，无任何读取 |
| `genePoints` | GameState | 同上（基因点系统根本没做） |
| `traits: string[]` | PlayerState | 同上 |
| `isVip` | PlayerState | 类型里声明，从未使用 |
| `isGodMode` / `isAutoMode` | PlayerState | 只初始化；UIOverlay 有 `onToggleGodMode`/`onToggleAutoMode` props 声明，但**组件体内零引用**（连按钮都没有） |
| `MAX_SQUAD_SIZE` / `ownerId` | world.ts / Entity | 战队系统预留 |
| `manualSquadSwitch()` | gameEngine.ts | 空桩，恒返回 false |
| `digestBasket()` | gameEngine.ts | 完整实现，但**没有任何调用入口**——鱼筐永远消化不掉 |

### 存档现状

`localStorage` 只用了两个键：
- `skillLevel`：读（initialState）+ 写（items.ts 漂流瓶），是通的
- `playerCosmetics`：**只有 diagnostics 调试脚本在读，全项目没有任何地方写**

也就是说 P0-1 刚接上的装扮面板，玩家搭配完关掉浏览器就没了。

### 结论

这类「看起来有、实际没接」的东西正是用户最初抱怨的「功能只实现了一半」，而且
和 P0-2b 发现的 `invulnerableTimer`（闪避技能是假的）是**同一个坑的第三次出现**。
死字段会持续误导后续开发，建议优先清掉而不是继续往上盖功能。

推荐顺序：清理死字段与接线残留（半天）→ 成就系统（EventBus 已就绪，纯订阅者，
零侵入，架构红利最大）→ 存档系统（半天，补上装扮持久化）→ 战队系统（要动 AI
敌我判定，成本高）。多鱼塘 / 排行榜 / 联机暂缓。

### 方法论

评估「下一步做什么」时不要直接引用既有路线图——路线图记录的是写文档时的判断，
会随着实现推进而过期。重新扫一遍 `grep` 死字段 / 空桩 / 只写不读的状态，往往能
发现更高价值的目标。

## 清理轮：发现并修复「构建入口指向旧代码」重大事故

用户选定先做清理。过程中发现 dist 产物 hash 连续三轮不变（index-DPcxROlg.js），抽查内容发现
**产物里没有任何 P0/P1 字符串**，反而包含 src 中已删除的旧逻辑（interactionType:"SHRINK"）。

**根因**：`index.tsx`（构建唯一入口）`import App from './App'` 指向**根目录重构前旧实现**
（1118 行旧 gameEngine.ts + 旧 components/ + 旧 types/constants）。重构是"兼容式"的，但只在
src/ 建了新实现，根目录旧文件原样留着。tsconfig/vitest 都只覆盖 src/，所以测试全绿是测新代码；
vite build 从 index.html → index.tsx 打的是根目录旧代码。
**dev server 同样走这个入口——开发者浏览器里跑的也一直是旧游戏。**

**修复**：index.tsx 改 `import App from './src/App'`；删除根目录 App.tsx / gameEngine.ts /
types.ts / constants.ts / components/（git 3694dd0 有底）。产物 hash → index-JWpBL7Hd.js（+7.8 kB），
新代码字符串全部验证在产物中。

**教训**：
1. 「build 通过」≠「build 出的是新代码」。产物 hash 跨轮不变是红灯；构建产物要抽查内容
   （搜一个本轮新增字符串）。验证脚本见 cleanup.test.ts 同期的 node 抽查命令。
2. 重构时"兼容门面"只该保留给类型转发，**旧实现文件必须删**，否则入口分裂。
3. e2e（Playwright）不 import 源码模块，走 dev server → 也受此影响，修复后自动生效。

## 「水槽隔离」排查轮（用户「水槽可以拖进去，现在貌似会被隔离在外面」）

### 排查结论：花瓣边界本身没有问题

实测数据（headless Chromium + window.__gs 调试句柄）：
- 全场景扫描：180 条鱼 0 条在界外、80 个障碍物 0 个跨界。
- 向右拖 45s 能贴到墙（d1911 / w2000），回拖中心 dist 正常递减。
- 小地图坐标换算与边界公式一致，无视觉错位。

### 真正的三个元凶（全部修复）

1. **开局商场陷阱（主凶）**：mouseRef 初始 (0,0) → 鱼开局自动朝屏幕左上角游，
   出生点 (3000,3000) 到深海商场只有 565px，约 3 秒撞进 → 状态切 SHOP、
   全世界暂停弹换装面板 → 玩家刚开局就被"关在"界面外。修复三连：
   - 商场搬家：MAP_CENTER-400 → -1500（离出生点 2124px）；
   - **E 键门闸**：进商场从"路过自动触发"改为"范围内按 E 上升沿触发"，
     平时只冒「按 E 进入商场换装」气泡。FrameInput 加 interact 字段，
     App→gameEngine 第 9 参透传，worldSystem 用模块级 prevInteract 做上升沿；
   - 交互圈放大 1.5 倍（r200→300），否则鱼速快时来不及按。
2. **岩石夹缝卡死**：障碍物互相深重叠会形成口袋，resolveObstacles 单遍把鱼从
   一块挤进另一块、来回抵消 = 玩家/AI 都被钉死（实测卡 14s+）。修复：
   生成时拒绝 dist < 0.7*(r1+r2) 的重叠对 + 整块含边缘在界内（buffer=radius+80）+
   resolveObstacles 两遍处理 + worldSystem 里改成先障碍后边界（边界有最终决定权）。
   实测修复后 48 块障碍最小重叠率正好 0.70。
3. **RAF 循环泄漏（结构性）**：App 的 gameLoop 每帧自排下一帧但 cleanup 只能取消
   第一帧 id，HMR/重挂载一次就泄漏一条链 → updateGame 每帧跑 N 次、鱼离奇加速。
   改为 `let alive` 生命标记写法。注意：**headless 浏览器 RAF 不限帧**，
   游戏按"每帧一步"设计（dt 恒 1），无高刷补偿——真实高刷屏（144Hz）会整体倍速，
   是 latent bug，已记入路线图待办。

### 调试方法论沉淀

- React 合成事件必须 `dispatchEvent` 到 canvas 且 `bubbles:true`，派发到 window 无效。
- E 这类**逐帧轮询**的键，keydown/keyup 同帧连发等于没按（要隔 ≥1 帧）；G 是事件驱动
  的 toggle，连发有效——同类按键要区分语义再测。
- agent-browser 页面状态跨 Bash 调用会重置，所有验证必须单条命令内完成全流程。
- 控制台探针（window.__probe）定位输入链断点比盲猜快。
