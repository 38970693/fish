1核心概念：塘 ≠ 海域

动手前先把两个容易混的东西分清，否则会做出重复功能。

海域 biome（早就有）鱼塘 pond（本轮新增）
是什么同一张地图内的四个生态区相互独立的游戏世界
怎么切游过去（位置决定）开局选择；或走塘际门
影响即时效果：速度 / 冷却 / 腐蚀 / 视野刷怪构成、得分倍率、难度、障碍密度

所以「多鱼塘」不是「在一张图里再划几个塘」——那和已有海域重复了。正确做法是 塘 = 一组世界参数：换塘就换一整套开局参数与世界内容。

3阶段 2a · 塘际传送门 + 世界重建

同尺寸、同形状，但内容整套重建——「换塘」这套机制才是最值钱的部分。

传送门被区分为两种，靠一个 kind 字段分流，缺省视为 LOCAL，因此旧存档与旧测试构造的门完全不受影响：

门kind行为
塘内门LOCAL本塘内随机传送（老行为）。只在本塘里挑目标——否则会把你丢到塘际门上，下一帧被动换塘。
塘际门POND每个「别的塘」一扇，摆在距塘中心 1150px 的环上，踏入即 pondTravel()。

换塘时保留什么、丢掉什么

保留玩家全部成长（体重 / 等级 / 技能 / 进化点 / 装扮）、分数、计时、战队成员
重建障碍物（按本塘 obstacleScale）、传送门、建筑
清空野鱼、道具、宝藏、危险事件、粒子、飘字
落地回塘中心、速度归零、落地保护、currentBiome 同步、铺底 12 条鱼

7还没做、以及为什么不顺手做

阶段 2b — 每塘独有地图尺寸 / 形状：暂缓。 要参数化 WORLD_SIZE / MAP_SHAPE_CONFIG / BIOME_BOUNDS， 并改掉 6 处写死的 Math.random() * WORLD_SIZE 刷点范围。 卡点：terrain.ts 在模块级就解构了形状 （const { BASE_RADIUS, PETAL_VARIANCE } = MAP_SHAPE_CONFIG），等于把形状写死在函数里， 参数化意味着十余个调用点一起改。牵动相机、小地图与地形校验，属真重构，需要单独一轮。

阶段 3a · 每塘独有内容

每塘独有生物 / 事件 / 建筑（深渊塘发光鱼群、沉船）。纯数据驱动，复用 2a 已建立的 obstacleScale 套路，不碰全局常量——成本最低、玩家感知最直接。

多人联机 · 另行立项

需要 WebSocket 服务端 + 房间 / 状态同步架构。仓库当前是纯静态 SPA，服务端早已不存在， 需从服务器、协议、断线重连从头设计，不在多鱼塘范围内。
